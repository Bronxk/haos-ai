## 1. OpenAI requests violate two provider contracts

### B01 — P1: every tool-enabled OpenAI scan/chat has an invalid schema

Locations: `custom_components/haos_ai/context.py:325`,
`custom_components/haos_ai/providers/openai.py:80`.

`get_automations` declares `query` in `properties`, but `required` is empty.
The adapter sends `strict: true` for every tool. OpenAI requires every property
to be required in strict schemas and explicitly rejects incompatible schemas.
Every scan/chat supplies this tool list, regardless of which tool the model
would select. Setup validation supplies no tools, so it can succeed first.

Evidence: enumerating `ContextEngine.tool_specs()` finds exactly this missing
required field. The rejection follows the documented API contract, not an
executed live request. Fix: require nullable `query` and add a schema-contract
check covering the actual full tool list.

### B02 — P2: reasoning items disappear during tool continuation

Locations: `custom_components/haos_ai/providers/openai.py:90`, `:116`, `:26`.

The adapter retains only function calls and text, dropping reasoning output
items. Its next input reconstructs function calls without the original output
sequence. Requests use `store: false`, with no response chaining or encrypted
reasoning continuation. Responses containing reasoning plus tools therefore
lose data required by the API. B01 currently masks this independent defect.

Evidence: a fake response containing a reasoning item and function call replays
only `function_call` and `function_call_output`. Exact remote error behavior was
not tested. Fix: implement documented stateless reasoning replay, preserving
the relevant complete output items and encrypted reasoning content.

Official contract for B01/B02:
[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling).

## 2. Approvals are not bound to the reviewed suggestion revision

### B03 — P1: recurrence can redirect approval from automation A to B

Locations: `custom_components/haos_ai/storage.py:359`,
`custom_components/haos_ai/websocket_api.py:319`,
`frontend/haos-ai-panel.ts:1185`.

Recurrence identity is only `(kind, title)`. A later scan replaces an existing
suggestion's automation, including its target, while preserving its ID. An open
browser still holds A's draft; approval sends that draft and suggestion ID,
without an expected target/revision. The backend resolves the current target B
and writes A's draft to B. The operation lock does not bind the reviewed target.

Executed with real suggestion merging and apply helper, mocked validation/file
primitives: `STALE APPROVAL WRITE: ('B', {'alias': 'A'})`.
Fix: immutable revisions and expected target/current-content hash; reject stale
approval. Different mutation targets must not share a recurrence identity.

### B04 — P2: queued approval survives capability revocation

Location: `custom_components/haos_ai/websocket_api.py:417`, lock at `:434`.

Permission is checked before waiting for the operation lock. Preferences can
disable the capability while an approval waits behind a scan, but it still
executes after acquiring the lock. Reviewer reproduced the decorated handler:
the apply sentinel ran with current `remove_entities=False`.
Fix: rederive the operation and recheck current permissions inside the lock.

### B05 — P2: recurring hygiene evidence changes while its operation stays stale

Location: `custom_components/haos_ai/storage.py:359`.

The recurrence merge updates evidence, rationale and confidence, but omits
`operation`. Same-title hygiene recommendations for A and then B keep A's
removal target under B's new evidence. Direct store reproduction produced two
occurrences with `operation.target_id='sensor.old_a'` after adding B.
Fix: include operation identity in deduplication and preserve coherent revisions
of evidence plus action; never combine a new explanation with an old target.

## 3. Automation writes and lifecycle can lose concurrent changes

### B06 — P2: HA's native editor and AI approval can overwrite each other

Location: `custom_components/haos_ai/automation_store.py:76`.

AI saves perform separate awaited reads and writes. The AI operation lock does
not coordinate with HA's native editor, whose config view owns its own
`mutation_lock`. A native save between the AI read and write is silently lost.

Executed with a temporary automation file and HA's native config `_write`:
insert `native-editor-save` after the AI read; successful AI save leaves IDs
`['original', 'ai-save']`. Fix: use a mutation path that coordinates with HA's
editor; another AI-only lock cannot solve this. Also protect the reviewed
current automation version against subsequent edits.

### B07 — P2: reconfigure can reload while an old operation remains active

Locations: `custom_components/haos_ai/config_flow.py:250`, `:279`, `:305`;
`custom_components/haos_ai/__init__.py:277`.

The HA reconfigure form checks busy before awaited provider validation, without
checking again afterward. The reviewer caused validation to acquire the
operation lock and observed the flow commit its update while busy. The panel
WebSocket path already has the missing second check.

Unload waits 30 seconds and then drops the runtime even if its operation is
still running. The old advisor retains its store and can save after replacement.
The reconfigure race was reproduced; cross-runtime disk loss is a control-flow
consequence, not a completed two-runtime disk reproduction.
Fix: recheck busy after validation and refuse unload or cancel/join tracked
operations before releasing their runtime/store ownership.

## 4. Blueprint validation differs from Home Assistant

### B08 — P2: invalid blueprint instances are reported as valid

Locations: `custom_components/haos_ai/automation_validation.py:64`, `:83`.

The blueprint branch checks input names and returns without substituting and
validating the resulting automation. A real installed zero-input blueprint
with instance `mode: bogus` returns `valid=True`; HA's schema rejects it. A
required input declared as `lamp: null` is also missed when absent, whereas
HA's `BlueprintInputs.validate()` raises `MissingInput`.
Fix: run native blueprint input validation/substitution and full automation
validation. Otherwise approval can persist an unusable automation as applied.

### B09 — P2: valid grouped blueprint inputs are rejected and misadvertised

Locations: `custom_components/haos_ai/automation_validation.py:58`,
`custom_components/haos_ai/context.py:679`.

Both inspect raw `metadata.input`, treating section names as input names.
Real blueprint section `section` containing input `lamp`, supplied as
`{lamp: light.test}`, is rejected for missing `section`; HA accepts the input.
The context tool also advertises the wrong names to the model.
Fix: use the flattened native `blueprint.inputs` interface in both paths.

## 5. Exclusions do not cover embedded references

### B10 — P2: ignored entity IDs still reach the provider in automation text

Locations: `custom_components/haos_ai/privacy.py:76`,
`custom_components/haos_ai/context.py:402`, `:744`.

Filtering removes only exact strings. An ignored `light.private` survives
inside `value_template: "{{ is_state('light.private', 'on') }}"` and the valid
comma-separated target `light.private, light.public`. The raw automation config
is returned even though its `referenced_entities` list is scrubbed.

Executed the actual context tool in HA with this exclusion: both embedded
references survived in outbound `data`; `privacy.redacted_fields` was empty.
This proves identifier/config-detail leakage, not leakage of that entity's
current private state. Fix: safely redact embedded references or withhold
automation configurations referring to excluded entities. Cover Jinja and
multi-target strings, not only structured lists.

## 6. Frontend async completions overwrite unrelated current state

### B11 — P2: validation overwrites newer edits or another suggestion's draft

Location: `frontend/haos-ai-panel.ts:1360`.

Start validation, then edit YAML or select another suggestion before completion.
The response unconditionally replaces current YAML and validation status.
Browser reproduction changed the draft to `alias: new unsaved edits`; response
restored `alias: first version` and `valid=true`. Cross-selection can put A's
validated draft into B's editor and approval target.
Fix: match suggestion ID, draft revision and request generation before applying
the result; invalidate it after edits/navigation.

### B12 — P2: chat results and loaded history can appear in the wrong thread

Locations: `frontend/haos-ai-panel.ts:843`, `:923`.

Sending in A and switching to B before completion appends A's reply into B's
current message list. Browser evidence: selected `audit-b`, messages
`['question B', 'ANSWER FOR A']`. Loading A then B also displays A's history if
A resolves last. Server persistence is separate; this is incorrect displayed
conversation context and can mislead subsequent messages.
Fix: capture thread identity, discard stale loads, and refresh the appropriate
thread rather than append into whichever thread is currently selected.

### B13 — P3: privacy receipt selection and displayed payload can disagree

Location: `frontend/haos-ai-panel.ts:947`.

Open receipt A then B; resolve B first and A last. Reproduction ends with
`selectedReceiptId=B` but `receipt.id=A`. The highlighted request and inspected
outbound payload differ. Fix: request generation/selected-ID check, invalidated
also when leaving the receipt view.

## 7. Deleted conversations can be recreated by a pending reply

### B14 — P2: delete returns success before the active chat recreates its thread

Locations: `custom_components/haos_ai/websocket_api.py:670`,
`custom_components/haos_ai/advisor.py:804`,
`custom_components/haos_ai/storage.py:422`.

Delete is not serialized against a pending chat. A fake provider gated on an
event reproduced deletion returning `{'deleted': True}`, followed by a new
thread containing only the assistant response when the provider finished.
`add_message` uses `setdefault` and silently recreates the removed thread.
Fix: serialize deletion or cancel/tombstone in-flight work and block its append.

## 8. Reload failure is hidden after a successful file write

### B15 — P2: frontend reports automation active despite failed HA reload

Locations: `custom_components/haos_ai/websocket_api.py:355`,
`frontend/haos-ai-panel.ts:1185`.

The backend correctly returns `reload_failed: true` when writing succeeds but
reload raises. The frontend ignores the response and shows the generic applied
notice. The applied marker prevents simply retrying approval. HA can continue
running the previous configuration while the UI suggests activation succeeded.
Evidence is the direct response-contract mismatch; no live home reload was
failed deliberately. Fix: consume the typed response, display saved-but-reload-
failed status and provide recovery that does not repeat the mutation.

## Recommended fix order

1. Bind approvals to immutable target/revision and coordinate automation writes.
2. Repair OpenAI schema and reasoning continuation; test actual outbound payloads.
3. Fix permissions/lifecycle, native blueprint validation and exclusion handling.
4. Guard frontend async results, chat deletion and reload-failure reporting.

Retain the existing passing tests. Add meaningful regression cases around these
interleavings and native contracts; passing mocked happy paths did not detect
the defects above. Do not treat the older `AUDIT.md` as evidence for this commit.
